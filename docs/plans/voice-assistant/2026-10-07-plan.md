# 1. Context

**Problem:**

Alarm và reminder đã tách ở service/database nhưng đang dùng chung active state,
notification listener, full-screen modal và callback snooze. Người dùng vì thế
nhận cùng một trải nghiệm cho hai nhu cầu có mức độ khẩn cấp khác nhau. Ngoài ra
có mismatch rõ ràng: UI báo alarm snooze 5 phút trong khi JavaScript fallback và
native Android đang dùng 10 phút.

**Affected Modules:**

- src/shared/stores/ — chuyển active alert ra khỏi alarm data store.
- App.tsx — route event và action theo alarm/reminder.
- src/features/alarm/ — giữ modal wake-up cho alarm, thêm action sheet nhẹ cho reminder.
- src/domain/services/notification_service.ts — policy schedule/snooze riêng cho từng loại.
- src/core/utils/native_alarm_bridge.ts và plugins/android-alarm/ — truyền đúng alarm snooze duration.
- src/domain/services/reminder_service.ts — giữ complete/cancel idempotent khi reminder được xử lý từ action sheet.

**Non-Goals:**

- Không thay đổi NLU, voice pipeline hoặc cách tạo alarm bằng giọng nói.
- Không thay thế Android AlarmManager/native playback đã hoạt động.
- Không triển khai recurring reminder mới khi chưa có UI và semantics cho từng occurrence.
- Không redesign toàn bộ AlarmListScreen.
- Không thêm dependency ngoài.

# 2. Constraints

**Language:** TypeScript strict, Kotlin cho native Android khi cần
**Architecture:** Feature-first React Native + Expo, Zustand stores, service/DAO separation

**Rules:**

- Giữ code và comment bằng English; tài liệu bằng Vietnamese.
- Reuse notification permission/cancel infrastructure hiện có.
- Không để reminder phụ thuộc vào useAlarmStore hoặc AlarmRingingModal.
- Không phá vỡ payload/type hiện có của native alarm.
- Mọi callback dismiss/complete/snooze phải an toàn khi được gọi lặp.
- Không sửa unrelated modules hoặc thay đổi schema SQLite trong task này.

**Performance Budgets:**

- Không thêm polling hoặc background timer mới cho reminder.
- Mỗi occurrence reminder chỉ tạo một scheduled notification chính; snooze là một lịch tạm thời riêng.
- Mở component tương ứng ngay sau event, không chờ network/LLM.

# 3. Conventions

**Naming:**

- Type/interface: PascalCase, ví dụ ActiveAlert, AlarmAlert.
- Function/variable: camelCase, tên biểu đạt intent, ví dụ openReminder.
- Service methods dùng động từ rõ loại: snoozeAlarm, snoozeReminder.
- Không dùng tên chung như handleSnoozeAlarm cho cả hai loại.

**Error Handling:**

- Service reject khi scheduling/action thất bại; UI giữ alert đang mở để retry hoặc đóng an toàn.
- Item không còn tồn tại được coi là action idempotent: log cảnh báo, đóng alert, không crash.
- Audio/TTS failure không được chặn dismiss/complete.
- Payload notification thiếu type hoặc ID không hợp lệ phải bị bỏ qua an toàn.

**Logging:**

- Reuse console.warn pattern hiện có cho native/audio/notification recoverable errors.
- Không log API key, user content nhạy cảm hoặc payload dư thừa.

**Testing:**

- Không có test runner trong package.json; dùng npm.cmd run typecheck, existing native check và smoke test trên Android nếu thiết bị/build khả dụng.
- Pure helpers/state transitions nên được tách để có thể kiểm thử độc lập nếu bổ sung test runner sau này.
- Acceptance criteria phải kiểm tra cả foreground, background/tap, native audio và duplicate event.

**Task Size:**

- Mỗi task tối đa khoảng 200 LOC code mới/chỉnh sửa, không tính test/manual notes.

# 4. Contracts

## Data Structure: AlarmAlert

AlarmAlert:
- type: alarm
- alarmId?: string — persisted alarm id when available
- label: string
- time: string — HH:mm
- spokenText?: string
- nativeAudio?: boolean
- occurrenceId?: string — native occurrence identity when available

Pre-conditions: type is alarm; time is display-safe; alarmId may be absent for test alarms.
Post-conditions: alert is rendered only by AlarmRingingModal.
Throws: no synchronous throw for missing optional IDs; action handlers report service errors.

## Data Structure: ReminderAlert

ReminderAlert:
- type: reminder
- reminderId?: string
- title: string
- time: string
- spokenText?: string

Pre-conditions: type is reminder; title is non-empty after fallback.
Post-conditions: alert is rendered only by ReminderActionSheet; no morning briefing is entered.
Throws: no synchronous throw for missing optional ID; complete/snooze action handles missing item safely.

## Shared type: ActiveAlert

ActiveAlert = AlarmAlert | ReminderAlert.

The discriminant type is the only routing source. UI components must not infer
alert kind from label, time or notification title.

## Interface: useAlertStore

- activeAlert: ActiveAlert | null
- openAlarm(params: Omit<AlarmAlert, 'type'>): void
- openReminder(params: Omit<ReminderAlert, 'type'>): void
- closeAlert(): void
- isSameActiveAlert(params: ActiveAlert): boolean

openAlarm/openReminder replace an empty or different alert; ignore the same active
occurrence to prevent duplicate overlays.

closeAlert is idempotent; null remains null.

isSameActiveAlert compares type plus stable ID and occurrence ID when present; no
network or side effect.

## Interface: NotificationService

- scheduleAlarm(alarm: Alarm, bodyMessage?: string): Promise<string>
- scheduleReminder(reminder: Reminder, bodyMessage?: string): Promise<string>
- snoozeAlarm(alarm: Alarm, fallbackMinutes?: number): Promise<void>
- snoozeReminder(reminder: Reminder, minutes?: number): Promise<void>

snoozeAlarm requires an active alarm ID; uses alarm.snoozeDuration when available
and defaults to 5 minutes. On Android, forwards the same minutes to native; on
Expo fallback, creates a temporary alarm notification.

snoozeReminder requires a reminder ID/title; defaults to 10 minutes; schedules a
temporary reminder notification without changing alarm state.

Both methods reject on scheduling failure; do not silently report success.

scheduleReminder creates one primary reminder notification and keeps the existing
none recurrence behavior unless a later plan adds recurrence semantics.

## Interface: NativeAlarmBridge

- snooze(id: string, minutes: number): Promise<void>

Pre-conditions: Android native module is available, id is active, and minutes > 0.
Post-conditions: native scheduler creates one snooze occurrence at now + minutes.
Throws: AlarmPermissionError/native action error when exact alarm permission or
active alarm is unavailable.

# 5. Target Architecture

**Components:**

- useAlertStore — owns only the active presentation alert and duplicate guard.
- AlarmRingingModal — wake-up presentation and alarm-specific voice/briefing flow.
- ReminderActionSheet — lightweight reminder completion/snooze presentation.
- App.tsx — maps notification/native events to alert state and delegates actions.
- NotificationService — shared permission/cancel utilities plus type-specific scheduling policies.
- NativeAlarmBridge/Kotlin scheduler — exact alarm and configurable native snooze.

**Interaction Flow:**

    Expo notification / NativeAlarmChanged
      -> App event adapter validates data.type and ID
        -> useAlertStore.openAlarm    -> AlarmRingingModal
        -> useAlertStore.openReminder -> ReminderActionSheet

    Alarm dismiss
      -> NativeAlarmBridge.stopRinging or notification cancel
      -> deactivate one-time alarm
      -> optional morningBriefingService
      -> useAlertStore.closeAlert

    Alarm snooze
      -> NotificationService.snoozeAlarm(alarm, alarm.snoozeDuration)
      -> native scheduler or Expo fallback
      -> useAlertStore.closeAlert

    Reminder complete
      -> ReminderService.complete(reminderId, true)
      -> cancel reminder and pending snooze notification
      -> useAlertStore.closeAlert

    Reminder snooze
      -> NotificationService.snoozeReminder(reminder, 10)
      -> useAlertStore.closeAlert

**Key Decisions:**

- Shared event transport is retained, but presentation and action policy are discriminated by type.
- The active alert state moves out of useAlarmStore so reminder actions cannot accidentally call alarm deactivation.
- Reminder does not reuse full-screen alarm UI; this is the main user-facing distinction.
- Native scheduler is changed only for passing snooze duration; exact alarm delivery and playback architecture remain intact.
- Reminder recurrence is explicitly deferred until its UI/series semantics are defined.

# 8. Task Specifications

## TASK-001: Active alert contracts and store migration

**Description:**

Create discriminated alert types and a dedicated Zustand store. Remove active
ringing state and openRingingAlarm/closeRingingAlarm ownership from the alarm
data store while preserving alarm list CRUD behavior.

**Input:**

- Existing RingingAlarmState contract from useAlarmStore.
- Notification/native payload shapes from App.tsx and native_alarm_bridge.ts.

**Output:**

- ActiveAlert contract and useAlertStore, consumed by TASK-003/TASK-004.
- useAlarmStore containing only alarm collection and alarm CRUD/state actions.

**Files:**

- src/domain/entities/alert.ts — create: alert union and payload types.
- src/domain/entities/index.ts — modify: export alert types.
- src/shared/stores/useAlertStore.ts — create: active alert state and duplicate guard.
- src/shared/stores/useAlarmStore.ts — modify: remove presentation alert state/actions.

**Responsibilities:**

- Implement openAlarm, openReminder, closeAlert, isSameActiveAlert.
- Preserve native occurrenceId and test alarm payloads without requiring persisted IDs.
- Use stable fallback labels/time for malformed but supported test payloads.

**Acceptance Criteria:**

- [ ] openAlarm(payload) -> activeAlert.type === alarm.
- [ ] openReminder(payload) -> activeAlert.type === reminder.
- [ ] Reopening the same type + id + occurrenceId -> no duplicate state transition.
- [ ] closeAlert() when already closed -> no error.
- [ ] Existing alarm list create/update/toggle/delete APIs remain type-safe.
- [ ] Edge cases #1, #2 and #6 from Section 9 are handled.

## TASK-002: Type-specific scheduling and configurable snooze

**Description:**

Separate alarm and reminder scheduling actions in NotificationService and make
native alarm snooze accept an explicit duration. Remove the reminder burst that
makes a normal reminder feel like a ringing alarm, while preserving the existing
alarm native/Expo delivery paths.

**Input:**

- Alarm and Reminder entities.
- Existing scheduleAlarm, scheduleReminder, native bridge and Kotlin snooze flow.

**Output:**

- snoozeAlarm and snoozeReminder contracts consumed by TASK-003/TASK-004.
- Native and Expo fallback scheduling with correct durations and channels.

**Files:**

- src/domain/services/notification_service.ts — modify: type-specific scheduling/snooze and one primary reminder notification.
- src/core/utils/native_alarm_bridge.ts — modify: snooze(id, minutes).
- plugins/android-alarm/AlarmScheduler.kt — modify: minutes-aware scheduling, no hidden 10-minute constant.
- plugins/android-alarm/AlarmPlaybackService.kt — modify: pass configured snooze minutes.
- plugins/android-alarm/AndroidAlarmModule.kt — modify: expose minutes argument.
- plugins/android-alarm/AlarmNotification.kt — modify: show the actual alarm snooze duration.

**Responsibilities:**

- Alarm snooze defaults to 5 minutes and uses alarm.snoozeDuration when present.
- Reminder snooze defaults to 10 minutes and uses reminder payload/content.
- Cancel/complete handles both the primary reminder notification and temporary snooze identifier.
- Keep alarm channel MAX/native exact behavior and reminder channel HIGH behavior.
- Do not implement recurring reminder semantics in this task; retain explicit none behavior.

**Acceptance Criteria:**

- [ ] snoozeAlarm(alarm) -> native/Expo trigger at now + alarm.snoozeDuration.
- [ ] snoozeAlarm(alarm) with missing/invalid duration -> uses 5 minutes, not 10.
- [ ] snoozeReminder(reminder) -> one reminder notification at now + 10 minutes.
- [ ] scheduleReminder(reminder) -> no second burst notification at T + 8s.
- [ ] Native notification label and JavaScript UI show the same snooze minutes.
- [ ] Native permission failure rejects and does not silently close the alert.
- [ ] Edge cases #3, #4 and #7 from Section 9 are handled.

**Input:**

- useAlertStore from TASK-001.
- Reminder scheduling/snooze contracts from TASK-002.

**Output:**

**Responsibilities:**

**Acceptance Criteria:**

- [ ] Reminder event -> ReminderActionSheet visible; AlarmRingingModal remains hidden.

- [ ] Reminder event with TTS enabled -> at most one speech invocation for the sheet.
- [ ] Reminder event with missing ID/title -> fallback copy, safe close on action.
- [ ] Edge cases #2, #4, #6 and #7 from Section 9 are handled.

# 9. Edge Cases

| # | Scenario | Expected Behavior | Handled In |
|---|----------|-------------------|------------|
| 1 | Native alarm event and Expo notification arrive together | One alarm alert keyed by occurrence/id; no duplicate modal/audio | TASK-001/TASK-003 |
| 2 | Notification has missing/unknown type or missing ID | Ignore or show safe fallback; never render the wrong component or crash | TASK-001/TASK-004 |
| 3 | Alarm snooze duration is missing, zero or invalid | Use 5-minute default consistently in JS/native/UI | TASK-002 |

| 5 | One-time alarm is dismissed; recurring alarm is dismissed | One-time deactivates; recurring remains active | TASK-003 |
| 6 | Alarm/reminder was deleted before the action completes | Close alert safely, log warning, do not crash | TASK-003/TASK-004 |
| 7 | Native permission, notification permission or TTS unavailable | Preserve core action; expose error/retry where relevant; no stuck modal/sheet | TASK-002/TASK-003/TASK-004 |
| 8 | Reminder has repeatInterval other than none but no supported UI/semantics | Do not silently pretend recurrence is implemented; preserve current explicit behavior and document follow-up | TASK-002/TASK-005 |
| 9 | App cold-starts from native alarm | Recover active native alarm and route only to alarm modal | TASK-003/TASK-005 |

# 11. Verification Plan

**Unit/Logic Checks:**

- useAlertStore — alarm/reminder discriminant, duplicate guard, idempotent close.
- NotificationService — alarm 5-minute default/configured snooze, reminder 10-minute snooze, one primary reminder schedule.
- Native bridge contract — minutes passed through and native notification text matches.

**Integration Checks:**

- Notification payload type -> correct component and action handler.
- Alarm dismiss/snooze -> correct alarm service/native side effect.
- Reminder complete/snooze -> correct reminder service/notification side effect.

**Manual / Smoke Tests:**

- Alarm in foreground -> full-screen wake-up modal, Tôi đã dậy rồi, morning briefing.
- Alarm in background/native Android -> exact alarm, native audio, snooze duration matches UI.
- Reminder in foreground -> compact action sheet, no repeated vibration/TTS.
- Reminder from notification tap -> action sheet, complete and 10-minute snooze.
- Duplicate event, missing permission, deleted item and TTS failure -> no crash/stuck UI.

**Success Criteria:**

- All automated/static checks available in the repository pass.
- Alarm behavior remains wake-up oriented and native-backed.
- Reminder behavior no longer opens the alarm modal or loops alarm-style audio.
- Snooze duration is consistent across UI, JavaScript fallback and native Android.
- No duplicate active alert for one occurrence.
