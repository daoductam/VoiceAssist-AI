## Detailed Findings

### 1. `App.tsx:handleDismissAlarm` Missing Alarm Deactivation
In `App.tsx:136-148`:
```typescript
const handleDismissAlarm = async () => {
  if (ringingAlarm.nativeAudio && ringingAlarm.id) {
    await NativeAlarmBridge.stopRinging(ringingAlarm.id);
  }
  if (ringingAlarm.type === 'reminder' && ringingAlarm.id) {
    try {
      await reminderService.complete(ringingAlarm.id, true);
    } catch (err) {
      console.warn('Failed to complete reminder:', err);
    }
  }
  closeRingingAlarm();
};
```
Reminders are marked completed (`reminderService.complete`), but alarms are completely ignored. A one-time alarm is left in `isActive = true`.

### 2. `hero_summary_helper.ts:getNextAlarmTrigger` Blind 24-Hour Roll
In `hero_summary_helper.ts:14-32`:
```typescript
while (
  targetDate.getTime() <= now.getTime() ||
  (alarm.repeatDays.length > 0 &&
    !alarm.repeatDays.includes((targetDate.getDay() + 6) % 7))
) {
  targetDate.setDate(targetDate.getDate() + 1);
}
```
For a one-time alarm (`repeatDays.length === 0`), if the alarm's time has passed today (e.g., it rang at 07:00 and it is now 07:01), `targetDate.getTime() <= now.getTime()` causes the loop to add 1 day and then terminate. As a result, the next trigger is computed as tomorrow (+23h 59m), causing the home screen hero card to state: "Còn 23 giờ 59 phút nữa...".

### 3. Native Android Alarm Stop Callback
When Android native alarm stops via notification action "Tắt chuông" or timeout, `syncNativeAlarm` in `App.tsx` sees `active === null` and closes the modal, but never deactivates the alarm in SQLite or the store.

### 4. Startup / Resync Rescheduling
In `alarm_service.ts:syncAllActiveAlarms()`, all alarms with `isActive = true` are rescheduled. If an expired one-time alarm wasn't deactivated, it gets rescheduled again for the following day.
